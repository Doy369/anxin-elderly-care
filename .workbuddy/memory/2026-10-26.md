## 小程序框架评审

用户提供两份模块表截图（微信发来），要求评审。表格覆盖：

| 模块 | 关键要求 |
|---|---|
| 登录与绑定 | 微信授权登录、亲情绑定 CRUD、一人可绑多老人、绑定关系校验 |
| 首页 | 4 个入口 + 未读消息红点，老人模式 3 步内可达任一 P0 |
| 诊断流程 | 问卷题目从 questionnaire 表动态加载、断点续答、提交测算分接口、报告图形化；4 场景 |
| 订单闭环 | 下单→选服务者（档案卡+双向确认）→状态机 5 态→凭证上传→双向评价；每态触发订阅消息 |
| 机构端 3 页 | 入驻资料上传、人员档案管理、接单与状态操作 |
| 管理端 4 页 | 内容发布/下架/排期、问卷配置、审核后台、看板 |
| 适老化 | 正文 ≥18pt、可点元素 ≥88px、高对比、首屏 <2s，组件库统一 |

**评审结论**：骨架方向对，但有 4 个会导致返工的问题。

### 四个硬问题

1. **角色模型未定义（最贵）**——老人是否独立微信账号没说。方案 A（独立账号）需要授权流程、越权校验、老人端页面、绑定表；方案 B（名下档案）全都省掉。表结构/权限/绑定校验/解绑后订单归属四项都取决于它
2. **管理端放小程序里架构错位**——内容发布/问卷配置/审核后台/看板本质是多行表格+批量操作+富文本+图表，小程序体验差、审核有风险、缺组件。建议改 Web 后台
3. **订阅消息做不到「每个状态变更触发」**——一次性订阅一次授权只能发一条；长期订阅仅限特定类目需申请。应只选 2-3 个关键节点 + 站内消息中心兜底
4. **适老化单位写错**——「18pt」小程序不用 pt；「88px」在 375 宽屏上是 1/4 屏宽，官方最小点击区是 44px（88rpx）。大概率把 rpx 当 px 了，按 88px 做按钮会排版失衡

### 验收标准不可测（4 处）

- 「老人模式 3 步内可达任一 P0」——P0 清单没给，「步」口径没定
- 「4 场景问卷全流程跑通」——4 个场景没定义
- 「全链路无人干预」——与双向确认、审核后台的人工环节矛盾
- 「管理员不碰代码可完成内容上线」——「内容」指图文/服务卡/问卷题，三者后台完全不同

### 其他缺口

- 状态机只写「5 态」没列具体状态，缺拒单/超时/改约/凭证驳回/退款，实际至少 7 态
- 诊断与订单之间断了，缺「诊断结论 → 推荐服务 → 直达下单」的转化路径
- 机构端 3 页装不下（入驻多步表单 + 人员列表详情 + 订单详情）
- 订单闭环没有「钱」：支付、退款、结算、抽成全部缺失
- 完全没提：服务者端、消息中心、支付退款、售后投诉、看板指标定义

### 与现有工程差距

现有「安心养老」7 页、纯本地存储、无后端、用户写死「王阿姨」。落地该框架需约 25–30 页 + 完整后端（多角色鉴权、状态机、文件存储、订阅消息）。后端是硬门槛。
