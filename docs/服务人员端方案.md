# 服务人员端方案

目标：让订单真的能被履约。现在订单提交后停在「待接单」，全系统没有一方能推进——`DEMO_MODE` 是让下单人假冒师傅点按钮，只能调试用。

好消息：云函数 `order` 的状态机里，`待接单→已接单`、`已接单→服务中`、`服务中→待评价` 三条已经限定为 `staff` 权限，服务端基础已经有了。缺的是「谁是 staff」和「师傅在哪操作」。

---

## 一、一期范围：抢单池，3 个页面

不做派单，因为派单需要机构管理员，而现在没有机构端也没有后台。抢单池最简单：已认证师傅能看到所有「待接单」的单子，谁先接归谁。等二期机构端出来，池子收窄成机构内池即可。

| 页面 | 内容 |
|---|---|
| `staff/home` | 上半：工单池（待接单，按上门时间排序）；下半：我的工单（进行中/已完成） |
| `staff/detail` | 客户信息（称呼、电话、地址、导航、备注）+ 时间 + 状态操作按钮 + 凭证预览 |
| `staff/record` | 写服务记录 + 拍照/选图上传 + 提交完成 |

工单卡上要能一眼看到：服务名、时间、地址、距离（可选）、备注里的房间号。

---

## 二、身份体系

```
users.role: 'user' | 'staff'
```

**激活方式（一期）**：在云函数里配一个 `STAFF_CODE`，师傅在「我的 → 服务人员入口」输入激活码后，`role` 升级为 `staff`，同时建一条 `staff` 记录（姓名、电话）。

为什么不做审核流程：没有后台界面，审核没去处。内测阶段师傅就几个，激活码够用。二期换成机构邀请码或后台审核。

**角色路由**：
- `app.js` 登录后把 `role` 放进 `globalData`
- 「我的」页加一行「服务人员入口」：`role==='staff'` 直接进 `staff/home`，否则弹激活码输入框
- 师傅不占 tab，走 `navigateTo`

## 三、云函数改动

在现有 `order` 云函数上加 4 个 action，不改状态机定义。

| action | 作用 | 权限 |
|---|---|---|
| `pool` | 待接单且未被接的订单列表 | 仅 staff |
| `mine` | `staffId` = 自己的订单 | 仅 staff |
| `accept` | 接单：待接单 → 已接单 | 仅 staff |
| `arrive` | 打卡：已接单 → 服务中，记录 `arrivedAt` | 仅 staff |
| `finish` | 完成：服务中 → 待评价，校验至少 1 张凭证 | 仅 staff |

### 接单必须防并发

两个师傅同时点「接单」，不能都成功。云开发的 `update` 会返回受影响条数，用它做乐观锁：

```js
const res = await db.collection('orders')
  .where({ _id: id, status: '待接单', staffId: '' })
  .update({ data: { status: '已接单', staffId: user._id, staffName: staff.name, acceptedAt: Date.now() } })

if (res.stats.updated === 0) {
  return { ok: false, message: '手慢了，这单已被接走' }
}
```

不要先 `get` 再 `update`，那中间有窗口期。

### 订单新增字段

```
staffId, staffName, acceptedAt, arrivedAt, finishedAt, media: [fileID]
```

`media` 直接存数组，不建 `order_media` 表——一期每单最多几张图，存文档里最简单。二期要审核、要统计图片数量时再拆表。

## 四、凭证上传

```
wx.chooseMedia({ count: 3, mediaType: ['image'], sizeType: ['compressed'] })
  → wx.cloud.uploadFile({ cloudPath: `orders/${orderId}/${Date.now()}.jpg` })
  → 拿到 fileID，存进 order.media
```

云存储权限设成「所有用户可读，仅创建者可写」即可——师傅写自己的，用户和机构读得到。

**完成时强制至少 1 张图**。没有凭证的完成无法追责，也无法做售后判定。

---

## 五、打卡定位：建议一期不做强制校验

`wx.getLocation` 要用得先在小程序后台申请「地理位置」接口权限，审核不一定批；室内定位精度也差，500 米判定容易误杀。

一期只记录 `arrivedAt` 时间戳，字段 `location` 留空。二期要加时，在云函数里用 Haversine 算距离，超阈值拒绝，前端把坐标一起传上来。

## 六、实施顺序

| 阶段 | 内容 | 产物 |
|---|---|---|
| 1 | 身份：`role` 升级、激活码、角色路由 | 「我的」页能进师傅端 |
| 2 | 工单池 + 接单（含防并发） | 师傅能接单，客户端看到状态变「已接单」 |
| 3 | 打卡 + 服务记录 + 凭证上传 + 完成 | 订单能走到「待评价」 |
| 4 | 关掉 `DEMO_MODE`，端到端联调 | 一单从下单到评价全人工走通 |

阶段 2 做完就能看到订单真的动起来了，是最有成就感的一步。

---

## 七、需要你定的三件事

1. **抢单还是派单** —— 建议抢单（不需要派单人）。若坚持派单，得先有机构端
2. **打卡要不要强制定位** —— 建议先不要（权限申请有风险、精度不可靠）
3. **完成是否必须传图** —— 建议必须，至少 1 张

---

## 八、这一期不做，但要提前知道

- 师傅的收入结算、接单上限、服务区域限制
- 拒单后的重新派单逻辑（状态机里有 `已拒单→待接单`，但没有自动重派）
- 服务质量评分对派单的影响
- 消息通知（现在只能靠师傅自己刷列表）
