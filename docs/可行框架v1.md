# 安心养老 · 可行框架 v1

> 目标：一套能真正交付的框架。不是把原表格做大，而是把不可行的部分换掉、把缺失的部分补上。

---

## 0. 相对原框架的六处改动

| 原框架 | 本框架 | 原因 |
|---|---|---|
| 四个并列模块（绑定/首页/诊断/订单） | 一条主线：评估 → 方案 → 下单 → 履约 → 复评 | 原设计里诊断和下单是断的，转化路径没接上 |
| 「一人可绑多老人」未定义主体 | 老人档案 = 数据主体，账号 = 操作者 | 不定这个，表结构无法开工 |
| 管理端 4 页放小程序 | 后台移出，做 Web | 表格/批量/富文本/图表，小程序做不了 |
| 每个状态变更都推订阅消息 | 3 个关键节点 + 站内消息兜底 | 一次性订阅一次授权只能发一条 |
| 5 态 | 8 态，含拒单/取消/售后 | 原 5 态缺异常路径 |
| 正文 ≥18pt、点击 ≥88px | 正文 ≥36rpx、点击 ≥88rpx | 小程序用 rpx，88px 是屏宽 1/4 |

## 1. 角色与权限

### 1.1 先把主体定死

**老人档案（elder）是数据主体，微信账号是操作者。** 订单、评估、记录全都挂在档案上，不挂在账号上。

这样解决了原框架最大的模糊点：

- 老人**可以不注册**，由子女建档并代办 → 零门槛
- 老人**也可以注册**，扫码把档案「认领」到自己的账号 → 双向可见
- 认领前后，订单归属都不变，只是多了一个能看的人

### 1.2 四类角色

| 角色 | 是谁 | 能做什么 | 用哪个端 |
|---|---|---|---|
| 用户 | 本人或家属 | 建档、评估、下单、查看、评价 | C 端小程序 |
| 服务人员 | 师傅 / 护工 | 接派单、打卡、填记录、传凭证 | 小程序（角色路由） |
| 机构管理员 | 服务商 | 接单、派单、人员管理、机构资料 | Web（推荐）或小程序 |
| 平台运营 | 你自己 | 审核、配置、改价、看板、兜底改状态 | Web 后台 |

### 1.3 绑定关系表（核心）

```
elder_bindings
  id, elder_id, user_id, relation, permission, status, created_at
```

- `relation`：父亲 / 母亲 / 配偶 / 本人
- `permission`：`owner`（建档人，可删档案）/ `member`（可看可下单，不能删）
- 一个 elder 可对多个 user（多子女），一个 user 可对多个 elder（多老人）
- 老人认领后，`elders.account_user_id = 该用户`，permission 升为 `owner`

**校验规则（原表只说「绑定关系校验」，这里写死）**：

1. 同一 user 对同一 elder 不可重复绑定
2. 非 `owner` 不能删除档案、不能解绑他人
3. 所有涉及 elder 的读写，必须校验 `user_id` 在该 elder 的绑定点内 → 越权返回 403
4. 档案存在未完成订单时，禁止删除（提示先完成或取消）

## 2. 业务主线

原框架把「诊断」和「订单」做成两个平行模块，中间没有连接。改成一条主线：

```
评估问卷 → 评估报告（风险项 + 建议） → 推荐服务（带参直达下单）
    ↑                                              ↓
    └────────── 服务后复评（可选） ←── 服务记录 ←── 履约
```

**关键点**：报告页每个风险项都挂「相关服务」按钮，带 `serviceId + elderId + assessmentId` 直接跳到下单页。这样评估不是白做的问卷，而是转化入口。

下单页回写 `assessment_id`，机构看到订单就知道是哪个评估结论来的，可以针对性报价。

## 3. 信息架构

### 3.1 C 端小程序 · P0（8 页，先能跑通）

| 页面 | 职责 | 关键点 |
|---|---|---|
| 首页 | 评估入口、服务分类、进行中订单、消息红点 | 老人模式：3 步内到任一 P0 功能 |
| 服务列表 | 分类筛选 + 搜索 | 支持从报告页带参进入 |
| 服务详情 | 包含项、服务流程、价格、机构 | 底部主按钮「立即预约」 |
| 下单 | 选档案、地址、时间、备注、费用预估 | 必填校验前置，不通过不提交 |
| 订单列表 | 全部 / 进行中 / 已完成 | 卡片直接显示状态与操作 |
| 订单详情 | 时间线、服务记录、凭证、联系、取消 | 状态决定显示哪些操作按钮 |
| 家人档案 | 增删改 + 健康备注 | 含绑定权限判定 |
| 我的 | 模式切换、大字开关、客服、入口 | 统计数字 |

### 3.2 C 端 · P1（4 页）

| 页面 | 职责 |
|---|---|
| 评估问卷 | 动态题目、进度条、断点续答 |
| 评估报告 | 评分、风险项、建议、推荐服务 |
| 消息中心 | 站内消息列表，与红点打通 |
| 评价页 | 双向评价，评分 + 标签 + 文字 |

### 3.3 服务人员端（5 页，复用同一个小程序，靠角色路由）

待办列表 / 工单详情（打卡 + 传凭证）/ 服务记录填写 / 历史工单 / 个人中心

> 服务人员与用户共用一个 AppID，登录后按角色进不同首页。不用第二个小程序，省一次审核。

### 3.4 机构端（5 页，建议 Web）

工作台 / 订单池（接单）/ 订单详情与派单 / 人员管理 / 机构资料

### 3.5 平台后台（7 页，Web）

订单总览（含改状态兜底）/ 服务与分类管理 / 机构与人员审核 / 问卷配置 / 内容与消息 / 数据看板 / 账号权限

> **为什么后台必须移出小程序**：内容发布要富文本编辑器，问卷配置要拖拽排序，看板要图表，订单总览要多行表格。这四样小程序都没有现成组件，自己写成本比 Web 高一个量级，微信审核对「管理后台」类功能也趋严。

## 4. 订单状态机（8 态 / 12 条转换）

```
待接单 → 已接单 → 服务中 → 待评价 → 已完成
  ↓        ↓
已拒单   已取消          已完成 → 售后中
```

### 4.1 转换表

| # | 当前 | 动作 | 目标 | 触发者 | 条件 |
|---|---|---|---|---|---|
| 1 | — | 提交订单 | 待接单 | 用户 | 必填项校验通过 |
| 2 | 待接单 | 机构接单 | 已接单 | 机构 | 有可用服务人员 |
| 3 | 待接单 | 机构拒单 | 已拒单 | 机构 | 必填拒单原因 |
| 4 | 待接单 | 用户取消 | 已取消 | 用户 | 免费 |
| 5 | 待接单 | 24h 无人接 | 已取消 | 系统 | 定时任务 |
| 6 | 已拒单 | 重新派单 | 待接单 | 运营 | 换机构 |
| 7 | 已接单 | 用户取消 | 已取消 | 用户 | 距上门 >24h 免费 |
| 8 | 已接单 | 人员打卡 | 服务中 | 服务人员 | 定位距服务地址 ≤500m |
| 9 | 已接单 | 超时未上门 | 已拒单 | 系统 | 超时段 2h |
| 10 | 服务中 | 提交服务记录 | 待评价 | 服务人员 | 至少 1 张凭证 |
| 11 | 待评价 | 用户评价 | 已完成 | 用户 | 评分 1–5 |
| 12 | 待评价 | 7 天未评 | 已完成 | 系统 | 默认好评 |

### 4.2 三条硬规则

1. **每次转换写 `order_logs`**：谁、什么时候、从哪态到哪态、备注。后台可查，纠纷时有据
2. **权限校验在服务端**，不靠前端藏按钮。前端只是不显示，服务端必须再判一次
3. **金额只在两种情况下变化**：取消扣费（P2）、机构改价（需用户确认）。其余状态流转不动钱

共 15 张（上表去重后）。

### 5.2 三个设计要点

1. **评估断点续答存服务端**，不是本地缓存。`assessments.answers_json` 每次答题后增量写，换设备也能续
2. **问卷版本化**：`questionnaires.version`，报告存 `questionnaire_id`，改版后历史报告按原版本渲染，不会算错分
3. **凭证与订单分离**：`order_media` 独立表，一张订单多张图，便于审核与追责

## 6. 订阅消息方案

原框架要求「每个状态变更触发」，微信做不到。改成：

**下单时一次性请求 3 个模板授权**（`wx.requestSubscribeMessage` 支持一次传多个 tmplId，用户逐条同意）：

| 节点 | 模板 | 发给谁 |
|---|---|---|
| 机构接单成功 | 订单状态通知 | 下单人 |
| 服务人员出发 / 上门 | 服务进度提醒 | 下单人 + 家属手机号短信（可选） |
| 服务完成 | 服务完成通知 | 下单人 |

**其余状态全部走站内消息**（`messages` 表 + 首页红点 + 消息中心页）。

**降级处理**：用户拒绝授权时，主流程照常走，只是不发订阅消息，站内消息仍在。不能因为没授权就不让下单。

## 7. 适老化规范（修正版）

### 7.1 单位全部改 rpx

| 原要求 | 修正为 | 说明 |
|---|---|---|
| 正文 ≥18pt | **正文 ≥36rpx**（18px） | 小程序不用 pt |
| 可点元素 ≥88px | **点击区 ≥88rpx**（44px） | 88px 是屏宽 1/4，过大 |
| 高对比配色 | **对比度 ≥4.5:1** | 可量化 |
| 首屏 <2s | **冷启动到可交互 <1.5s**（4G / 中端安卓） | 补测量条件 |

### 7.2 组件库（五类，统一封装，不逐页写）

`btn` / `card` / `form-item` / `tag` / `empty`

每个组件内置三档尺寸：标准 / 大字（×1.24）/ 超大（×1.4）。页面只传 `size`，不各自写样式。

**这条是原框架唯一定得对的要求**，保留，但要用组件实现而不是复制粘贴——现有工程是逐页写 `.bigfont` 覆盖块，改一处要同步七处，这是已经产生的技术债。

### 7.3 老人模式额外约束

- 主按钮高度 ≥96rpx，文字永远不省略
- 不用纯图标按钮，图标必须配文字
- 表单错误提示用弹窗，不用页面内红字（容易看不到）

## 8. 分期计划

| 期 | 内容 | 产出 | 可验收 |
|---|---|---|---|
| **一期** | 登录、家人档案、服务浏览、下单、订单列表详情、后台手改状态 | 8 页 + 后台 2 页 | 能完整走一单，运营手动推进状态 |
| **二期** | 评估问卷、报告、推荐服务直达下单 | +3 页 + 后台问卷配置 | 填完问卷能跳到对应服务下单 |
| **三期** | 服务人员端、打卡凭证、订阅消息、评价 | +5 页 | 师傅自己接单打卡传图，用户收到通知 |
| **四期** | 支付退款、结算、看板、多机构 | +后台 5 页 | 线上收款，平台能看经营数据 |

**一期不要做支付**。微信支付需要商户号、营业执照、对公账户，周期通常 2–4 周，会卡住整个上线。一期用「预约 + 线下/到店支付」，先把履约跑通。

## 9. 后端选型

这是硬门槛，必须先解决。三选一：

| 方案 | 优点 | 代价 | 适合 |
|---|---|---|---|
| **微信云开发**（推荐） | 免域名备案、原生 SDK、自带数据库/存储/定时任务、支持订阅消息、有免费额度 | 绑定微信生态，迁移成本高 | 小程序单端项目 |
| WorkBuddy 云服务 | 托管、免运维、含 LLM | 需要点开通确认 | 想快速起步 |
| 自建后端 | 完全可控、可扩展 | 需域名 + ICP 备案 + 服务器 + 运维 | 长期多端 |

**推荐微信云开发**：小程序原生配套，不用买域名、不用备案，`wx.cloud.callFunction` 直接调，文件和数据库都是现成的。MVP 阶段免费额度基本够用。

## 10. 验收标准（可测版）

把原表里不可测的四条改写：

| 原表述 | 改为 |
|---|---|
| 老人模式 3 步内可达任一 P0 功能 | 老人模式下，从首页到「下单完成」≤ 4 次点击；P0 功能清单见 3.1 表 |
| 4 场景问卷全流程跑通 | 3 个场景（居家安全 / 自理能力 / 慢病照护）各 15–20 题；从首页到报告 ≤90 秒；杀进程后返回可续答且答案不丢 |
| 全链路无人干预 | 一期允许运营在后台改状态，但每次改动必留日志；三期后除「拒单」「售后」外无需人工 |
| 管理员不碰代码可完成内容上线 | 后台新增一个服务并上架，全流程 ≤5 分钟，无需发版 |

**新增 4 条**：

1. 状态机 12 条转换逐条有权限校验，越权调用返回 403 并记录日志
2. 用户 A 修改参数无法读取用户 B 的订单 / 档案（越权测试）
3. 订阅消息未授权时主流程不阻塞，站内消息仍到达
4. 抽查 10 个页面，正文 ≥36rpx、点击区 ≥88rpx、对比度 ≥4.5:1 全部达标

## 11. 与现有工程的关系

现有「安心养老」7 页、本地存储、用户写死。可以复用：

- ✅ **视觉与配色**：白绿体系、`docs/color-palette.md` 整套色板
- ✅ **页面骨架**：首页、服务列表、下单、订单列表、订单详情、家人档案、我的 —— 这 7 页的结构基本对得上本框架 P0
- ✅ **数据形态**：`utils/data.js` 的 12 个服务条目可直接迁成服务表种子数据
- ❌ **存储层**：`utils/store.js` 需整体替换为云端调用
- ❌ **用户体系**：现在写死「王阿姨」，要换成微信登录 + 档案绑定
- ❌ **状态机**：现在只有 5 个字符串状态，无转换校验、无日志

**迁移路径**：保留界面，把 `utils/store.js` 换成云开发 SDK 封装，页面调用方式不变（该文件本来就是按接口形态设计的）。再补状态机校验与新页面。

## 12. 一句话总结

原框架的方向没错，问题在于**把不可行的技术动作写成了验收标准**（每态订阅消息、小程序做后台、88px 点击区），以及**跳过了最贵的决策**（老人是不是账号）。

这份框架的做法是：先定主体和角色 → 用一条主线串起评估与下单 → 状态机补全异常路径 → 后台移出小程序 → 消息降级 → 单位改对 → 分期上线。
