# 服务端 v2 设计

## 一、为什么现在要改

现有服务端是按「老人档案 → 服务」设计的，新前端的主线变成了「房子 → 房间 → 服务」。错位已经产生三个可验证的问题：

| # | 问题 | 代码位置 | 后果 |
|---|---|---|---|
| 1 | 照片按 `userId` 归属 | `cloudfunction/room` 里 `where({ userId: user._id })` | 子女用自己微信登录，看不到父母的房子；换账号就全丢 |
| 2 | 订单只有 `address` 字符串，没有 `homeId` | `order.create` 的字段清单 | 师傅接单后想对照「浴室照片」看现场，关联不上 |
| 3 | 隐患勾选存在 `wx.setStorageSync` | `pages/room/room.js` | 师傅看不到用户自查了什么，「已检查 1/4」只是装饰 |

根因一句话：**数据主体从「人」变成了「房」，但表结构还挂在人身上。**

---

## 二、目标实体关系

```
用户 ──管理──> 房屋 ──包含──> 房间资产（照片 + 隐患勾选）
                 └──产生──> 订单 ──引用──> 服务项目
                              └──指向──> 老人档案（可选）
```

核心改动：**房屋成为一等实体**，照片、勾选、订单全部挂 `homeId`，不再挂 `userId`。

---

## 三、表清单

| 表 | 作用 | 关键字段 | 现状 |
|---|---|---|---|
| `users` | 账号 | openid, role | 已有 |
| `homes` | 房屋 | address, area, floor, elevator, ownerUserId | **新增** |
| `room_assets` | 房间资产 | homeId, roomType, photoFileID, checks[] | **新增**（合并现有 room_photos + 本地勾选） |
| `elders` | 老人档案 | homeId（新增） | 已有，加字段 |
| `orders` | 订单 | homeId, roomType, quoteAmount, designOrderId | 已有，加字段 |
| `order_logs` | 流转日志 | — | 已有 |
| `services` | 服务目录 | code, pricing, price | **二期**（一期继续用 design.js 静态） |
| `staff` | 服务人员 | userId, name, phone, status | **二期** |

### room_assets 为什么不拆两张表

一条记录对应一间房：

```js
{
  homeId: 'h_123',
  roomType: 'bathroom',
  photoFileID: 'cloud://xxx',
  checks: [0, 2],           // 已勾选的隐患项下标
  photoUpdatedAt: 1761000000,
  checksUpdatedAt: 1761000000
}
```

找「浴室的照片和检查情况」一次查询就够。拆成 photos / checks 两张表，读一次页面要查两次，没有收益。

## 四、三条流程变化

### 4.1 下单必须挂房屋

`booking` 提交时带 `homeId`（一期取用户唯一那套房）。之后：

- 订单详情能显示「浴室 · 已检查 2 项」
- 师傅端能顺着 `homeId + roomType` 直接看到现场照片
- 同一套房的多个订单可以聚合统计

### 4.2 报价：一期只加字段，不加状态

改造类服务是上门评估后报价，现在 `amount` 一直是 0，只能显示「上门评估后报价」，没有下文。

建议加两个字段：

```js
quoteAmount: 0,              // 师傅评估后填的实际价格
quoteStatus: 'none'          // none | quoted | confirmed
```

**不要新增状态。** 理由：没接支付之前，「确认报价」只是记个字段，用户的确认没有金额变动作为支撑；等二期接微信支付，再把它升级成 `待确认报价` 状态。状态机每加一态，权限矩阵、日志、前端按钮显隐都要改一遍，收益不匹配。

### 4.3 设计转施工

设计订单完成后，改造订单带 `designOrderId`：

- 改造单详情显示「已抵扣设计费 ¥199」
- 结算时（二期）按抵扣后的金额收款
- 设计订单详情显示「已转施工，扣除抵扣后实收 ¥X」

现在两张单毫无关联，用户说不清 199 抵到哪去了。

## 五、迁移方案

现有数据基本都是测试数据，迁移成本很低，建议直接重建而不是兼容：

1. 新建 `homes`，用户首次登录自动建一套默认房，地址留空待填
2. `room_photos` → `room_assets`，加 `homeId` 和 `checks` 字段
3. `orders` 加 `homeId`，历史订单置空，查询时 `homeId` 为空按 `userId` 兜底
4. `elders` 加 `homeId`，允许为空（有些老人档案只是联系人信息）

`login` 云函数里负责自动建表，新增集合名追加到 `COLLECTIONS` 数组即可。

## 六、分期

| 期 | 内容 | 产出 |
|---|---|---|
| 一期 | `homes` + `room_assets`，订单挂 `homeId` | 照片和勾选跨设备可见，师傅能看到现场 |
| 二期 | 报价字段 + 设计转施工关联 | 改造单能显示实际报价，设计费能抵扣 |
| 三期 | `staff` 表 + 服务人员端 | 订单能真的被接单履约 |
| 四期 | `services` 入库 + Web 后台 | 运营能自己配服务、改价、审核 |

一期的改动量最小，但它解锁的是「数据归属正确」——后面三期四期都建在这个地基上。**地基错了，后面全是补丁。**

---

## 七、需要先定的两件事

1. **一人是否支持多套房** —— 影响 `home_access` 要不要独立成表。建议一期只做一套（`homes.ownerUserId` 直接关联），二期再拆权限表。
2. **地址怎么填** —— 一期手填文本框最省事；要做地址簿或地图选点，得接腾讯位置服务，是另一个工作量。
