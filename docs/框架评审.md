# 小程序框架评审

评审对象：模块表（登录与绑定 / 首页 / 诊断流程 / 订单闭环 / 机构端 / 管理端）+ 适老化硬性要求。

结论：**业务闭环的骨架是对的**，诊断→下单→履约→评价这条主线成立，机构端与管理端的分层也对。但有 4 个问题会导致返工，其中 2 个是架构级的；另有 5 处验收标准在交付时无法判定。

---

## 一、会导致返工的问题

### 1. 角色模型没定义，这是最贵的一个

表格写「一人可绑多老人」「角色切换」「绑定关系校验」，但没回答一个前置问题：**老人是不是独立的微信账号？**

两种理解的数据模型完全不同：

| | 方案 A：老人有独立账号 | 方案 B：老人只是子女名下的档案 |
|---|---|---|
| 绑定动作 | 老人扫码确认，需授权 | 无需绑定，直接新增档案 |
| 「解绑」含义 | 解除账号关系 | 删除档案 |
| 订单归属 | 老人，子女是代操作人 | 子女 |
| 历史订单 | 解绑后仍留在老人侧 | 跟着档案一起消失 |
| 是否需要老人端页面 | 需要 | 不需要 |
| 数据表 | 用户表 + 绑定关系表（多对多） | 用户表 + 档案表（一对多） |

差别是：页面数、权限判定逻辑、绑定校验规则、以及「解绑后订单归谁」这类必须写进代码的规则。

**建议**：先定 A 还是 B。如果走 A，「绑定关系校验」要写明校验什么——是防重复绑定、防越权查看、还是防绑定非本人？

### 2. 管理端放在小程序里，架构错位

管理端要「内容发布/下架/排期、问卷配置、审核后台、看板」。这些操作的本质是：多行表格、批量勾选、富文本编辑、数据图表。

小程序做这些有三重问题：
- 体验差：表格横向滚动、批量操作没有右键/多选习惯，改一条内容要点五六层
- 审核风险：微信对「内容管理后台」类功能审核趋严，容易被判定为不符合小程序类目
- 开发成本：小程序没有成熟的表格、富文本、图表组件，全都得自己写

**建议**：管理端做 Web 后台（React/Vue + 现成组件库），和云端共用一套 API。机构端也建议评估——3 页里「入驻资料上传」是个多步表单，小程序够用但 Web 更顺。

### 3. 订阅消息做不到「每个状态变更触发」

微信订阅消息有硬限制：
- **一次性订阅**：用户点一次「允许」，只能发一条消息，发完即失效
- **长期订阅**：仅对特定类目开放（政务、医疗、交通、教育等），需要申请，普通养老类目大概率批不下来

订单 5 态如果每态都推，用户每次下单要授权 5 次，实际使用中没人会这么做。

**建议**：只选 2–3 个关键节点用一次性订阅（接单成功、服务人员出发、服务完成），其余状态用**站内消息中心**兜底。这也顺带解释了首页的「未读消息红点」——它需要配套的消息模块，但框架里没有。

### 4. 适老化要求的单位写错了

原文：「正文字号 ≥18pt、可点元素 ≥88px」。

- **pt 是印刷/iOS 单位**，小程序用的是 rpx 和 px。18pt 折算约 48rpx，但如果开发按 pt 理解会算错
- **88px 太大了**。在 375pt 宽的屏幕上，88px 是屏幕宽度的近 1/4。微信官方建议的最小点击区是 **44px（即 88rpx）**。这里大概率是把 rpx 当成了 px

如果按 88px 实现，按钮会大到排版失衡；如果按 88rpx 实现，才符合规范。

**建议**：统一改成 `正文 ≥ 36rpx（18px）`、`点击区 ≥ 88rpx（44px）`。另外「首屏加载 < 2s」要写明测试条件——冷启动还是热启动、4G 还是 WiFi、哪档机型，否则无法验收。

## 二、交付时才发现的问题

### 5. 验收标准有四处不可测量

| 原文 | 问题 |
|---|---|
| 老人模式 3 步内可达任一 P0 功能 | 「P0 功能」没有清单；「步」是点击次数还是页面层级也没定 |
| 4 场景问卷全流程跑通 | 4 个场景是哪 4 个，没有定义 |
| 单从下单到评价全链路无人干预 | 与「双向确认」「审核后台」矛盾——这两处本就是人工 |
| 管理员不碰代码可完成内容上线 | 「内容」指什么没说：图文资讯、服务卡片、还是问卷题目？三者后台完全不同 |

### 6. 订单状态机只说了「5 态」，没列出这 5 态

已知节点是：下单 → 选服务者 → 双向确认 → 凭证上传 → 双向评价。但缺了：
- **服务者拒单**之后走哪
- **超时未确认**是否自动取消
- **老人取消**在哪个阶段还能免费取消
- **改约**是否算新订单
- **凭证被驳回**怎么回到上一态

5 态大概率不够，实际至少需要：待确认 / 已接单 / 服务中 / 待评价 / 已完成 / 已取消 / 已拒单 七态起步。

### 7. 诊断和下单之间是断的

框架里「诊断流程」和「订单闭环」是两个并列模块，没有衔接。

但实际上，**诊断出问题 → 推荐对应服务 → 直接下单**才是这个产品的核心转化路径。如果做完问卷只给一份报告，用户还得自己跑去「找服务」重新找，转化就断了。

**建议**：报告页每个结论项都挂「相关服务」入口，带参数直达下单页。

### 8. 机构端 3 页装不下

「入驻资料上传」通常是多步表单（营业执照、资质证书、服务人员信息、服务范围），一页做不完。「人员档案管理」至少要有列表页 + 详情编辑页。「接单与状态操作」要有列表 + 订单详情 + 操作。

3 页是极限压缩，实际会变成三页超长滚动。建议按 5–6 页规划。

### 9. 订单闭环里没有「钱」

框架列了下单、选人、确认、凭证、评价，但**没有支付、退款、结算**。

养老服务是付费交易：什么时候付款（下单预付还是服务后付）、服务者拒单谁退款、机构怎么结算、平台抽成多少——这些不在状态机里，但每一笔订单都要走。

## 三、完全没提到的模块

1. **服务者端**：机构端能接单，但服务者本人（护工、师傅）怎么收到派单、怎么上传凭证？如果靠机构代操作，机构端页数还要涨
2. **消息中心**：首页有未读红点，但框架里没有消息列表页
3. **支付 / 退款 / 结算**
4. **售后与投诉**：服务不满意走什么流程
5. **数据埋点与看板指标**：管理端有「看板」，但看什么指标没定义

---

## 四、与当前工程的差距

现有工程是「安心养老」，7 个页面、纯本地存储、无后端。

要落地这个框架，缺口是：

| 能力 | 现状 | 框架要求 |
|---|---|---|
| 页面数 | 7 | 约 25–30（C 端 8 + 机构端 5 + 管理端 4+ + 服务者端 + 消息） |
| 后端 | 无（wx.setStorageSync） | 必须：多角色鉴权、状态机、文件存储、订阅消息 |
| 用户体系 | 无（写死「王阿姨」） | 微信授权登录 + 多角色 |
| 问卷 | 无 | 动态从表加载、断点续答、服务端算分 |
| 文件上传 | 无 | 机构资质、服务凭证 |
| 消息 | 无 | 订阅消息 + 站内消息 |

其中**后端是硬门槛**。之前两次云服务开通确认都取消了，所以现在连「子女在自己手机上看父母订单」都做不到——数据各存各的手机。

---

## 五、建议的推进顺序

1. **先定角色模型**（老人是否独立账号）—— 这一个决定影响后面所有表结构
2. **补全状态机**，把 5 态画成完整流转图，标注每个转换的触发者和条件
3. **修验收标准**，把「P0 清单」「3 步口径」「4 场景」写死
4. **管理端改 Web**，机构端评估是否也改
5. **开通后端**，这是所有多角色、多设备功能的前提
6. **再谈页面实现**

框架本身不用推翻，补上这些缺口就能开工。
